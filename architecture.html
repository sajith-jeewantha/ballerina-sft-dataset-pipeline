Ballerina SFT Dataset Pipeline

A pipeline that builds a grounded question-and-answer dataset for fine-tuning a Ballerina small language model. It scrapes official sources, generates questions from heading-aware chunks, answers each question from the same chunk with a source citation, compiles the code, and tracks every step in one SQLite database with an HTML report.

Repository: github.com/sajith-jeewantha/ballerina-sft-dataset-pipeline v2.1: Q&A pipeline on SQLite; see the changelog

Principles

Grounded answers, visible progress and cheap test runs.

Official sources only

ballerina.io (learn, by-example, spec 2024R1), Ballerina Central and the ballerina-platform GitHub org. No blog.

Grounded and cited

Each answer is generated from its question plus the exact chunk the question came from, and ends with Source: <url>.

Every record has a status

Pages, chunks, questions, answers and runs move through explicit statuses with timestamps.

Small runs first

Limits in .env bound each run, are printed at startup and are stored with the run.

Verify the code

Ballerina code in answers is compiled with the real bal toolchain: valid, invalid or not checked.

Simple to operate

One CLI, one database file, one self-contained HTML report. Re-runs never repeat finished work.

End-to-end data flow

Every phase reads from and writes to data/pipeline.db. The report is rebuilt from it after every command.

Why BBE comes from GitHub: ballerina.io ships Ballerina-by-Example explanations only inside compiled JavaScript. The page list comes from the sitemap, but the explanation, code and output come from ballerina-distribution/examples/<name>/, exactly as written, and answers cite the ballerina.io URL.

Sources

From the sitemap, only /learn/, /learn/by-example/ and /spec/lang/2024R1/ are kept. Old version paths, robots-disallowed paths, index pages and duplicates are skipped.

Ballerina by ExampleExplanation + code + output, verbatim (highest priority)Sitemap list; files from ballerina-distribution via the GitHub blobs API
Learn docsGuides, tools, packages, tutorials, integration patternsballerina.io page's embedded Markdown source

Storage

One SQLite file. Every row has a status and created_at / updated_at. Columns are documented in docs/schemas.md.

erDiagram
  PAGES ||--o{ CHUNKS : "split into"
  CHUNKS ||--o{ QUESTIONS : generates
  QUESTIONS ||--o| ANSWERS : "answered by"
  RUNS ||--o{ LLM_USAGE : records
  PAGES { string url "fetched, chunked, empty, duplicate, blocked, failed" }
  CHUNKS { string text "pending, questioned, too_small, failed, stale" }
  QUESTIONS { string question "pending, answered, failed" }
  ANSWERS { string answer "not_checked, valid, invalid" }
  RUNS { string command "running, succeeded, failed" }
  LLM_USAGE { float cost_usd "ok, error" }

Limits for small runs

Set in .env, printed at startup, stored on every run. The answer phase answers every pending question, so it is naturally limited by LIMIT_GENERATING.

VariableDefaultMeaning
LIMIT_SCRAPE_PAGES20Max pages to download per source per run (0 = no limit)
LIMIT_GENERATING10Max questions to generate per run (0 = no limit)
QUESTIONS_PER_CHUNK3Questions generated from each chunk
REQUEST_DELAY_SECONDS1Polite delay between requests
GITHUB_TOKEN-GitHub API: 5,000 requests/hour instead of 60

The report

A short terminal summary after every command, and reports/report.html: one file, no server, opens in any browser.

Contents

  • Pages scraped: total, per source and status, failed URLs with errors
  • Chunks per source
  • Questions per source, category and difficulty
  • Answers: answered, pending, failed; validation results
  • Run history: start, duration, limits, items processed
  • Tokens and cost per phase
  • 5 random Q&A samples to spot-check

Configuration

Precedence: environment variable > .env > config/pipeline.yaml > code default. Empty values in .env are ignored. Values are checked at startup.

.env (never committed)

OPENROUTER_API_KEYLLM access
LLM_BASE_URLOpenRouter by default; any OpenAI-compatible endpoint works
QUESTION_GEN_MODEL · ANSWER_GEN_MODELGeneration models
GITHUB_TOKENGitHub API rate limit
LIMIT_* · QUESTIONS_PER_CHUNK · REQUEST_DELAY_SECONDSRun limits

config/pipeline.yaml (committed)

sourcesOrder, sitemap filters, GitHub repo patterns and file globs, Central orgs
crawlUser-Agent, robots.txt, exempt API hosts, listing cache
chunkmax_tokens (800), min_tokens
generateConcurrency, requests per minute, temperatures, dedup threshold, pricing
validatebal path, workers, timeout, heap

sftOutput dir, eval share (split by page), strip Source: line, system prompt

How to run

Start with the default limits (10 questions), check the report, then raise them.

1

Set up once

git clone https://github.com/sajith-jeewantha/ballerina-sft-dataset-pipeline.git
cd ballerina-sft-dataset-pipeline
python3.11 -m venv .venv && source .venv/bin/activate
pip install -e shared -r scraper/requirements.txt -e scraper \
  -r sft-dataset-generator/requirements.txt -e sft-dataset-generator -r requirements-dev.txt
cp .env.example .env   # API key, models, GITHUB_TOKEN, limits
2

Run all phases, or one at a time

sftgen run-all
# or: sftgen scrape · generate-questions · generate-answers · validate · export · export-sft
3

Check progress

sftgen report
open reports/report.html

Re-running and resuming

PhasePicks up
scrapePages not yet stored, and failed ones. --refresh re-checks stored pages: unchanged by blob SHA or package version (no request), HTTP 304, or identical content hash.
clean + chunkPages with status fetched. Re-chunking keeps unchanged chunks and their questions; removed ones become stale.
generate-questionsPending chunks without questions; failed calls retried up to 3 times.
generate-answersPending questions; --retry-failed adds failed ones.
validateAnswers not yet checked; --recheck re-validates all.
CachesLLM responses and compile results on disk, so repeated work costs nothing.

Reliability, politeness and safety

ConcernApproach
Scrapingrobots.txt checked before every web page (repeated User-agent: * groups merged). One honest User-Agent, REQUEST_DELAY_SECONDS between requests. No proxies, no User-Agent rotation. Documented JSON APIs are exempt from robots.txt.
FailuresRecorded on the page or question with the error, shown in the report, retried next run. One failure never stops a run.
HTTP retriesBackoff that honours Retry-After and GitHub's rate-limit reset.
LLM callsConcurrency cap plus requests-per-minute limit; SDK retries; JSON output validated; tokens and cost stored per call.
Compiling generated codeCompile only, never run. Temp folder, --offline first, timeout, -Xmx1g, 2 workers, secrets removed from the environment.
SecretsOnly in the environment. Never logged or stored in the database.
