Ballerina SFT Data Pipeline

A pipeline that builds a traceable, compiler-checked fine-tuning dataset for a Ballerina small language model. It takes upstream sources through collect, clean, extract, chunk, embed, generate, validate, judge and export.

Implemented in Phase 5; see CHANGELOG.md

Principles

Data quality, correct code and traceability matter more than volume.

Source first

Pull clean upstream files (GitHub repos, the Central API). The HTML crawl only covers sites with no source files.

Raw is never modified

data/raw is append-only. Every other folder can be deleted and rebuilt from it.

One stage, one output

Stages communicate only through schema-checked files and a manifest.

Idempotent and resumable

IDs are computed from content, and work already done is skipped. A crash loses at most the item in progress.

Verify, don't trust

The compiler checks the code, and a judge from a different model family scores each answer. Every score is kept.

Traceable

Every training row links back to seed → chunk → document → raw → commit SHA or URL.

End-to-end data flow

Collectors write raw records. Each stage after that reads the previous stage's file and writes its own.

Changed order: the pipeline runs validate → judge, not judge → validate. The compiler and static checks are free and deterministic, so candidates that fail them are rejected before any judge tokens are spent. Both results are still stored on every record.

Where data is stored

Everything under data/ is gitignored. GCS can optionally mirror the same layout.

data/
├── raw/                          # immutable, append-only
│   └── {github|central|web}/{run_id}/part-00000.jsonl.gz + _manifest.json
├── clean/   documents.jsonl · code_examples.jsonl · _manifest.json
├── chunks/{chunker-version}/   chunks.jsonl · _manifest.json
├── chroma/                       # derived index, safe to delete and rebuild
├── sft/{run_id}/
│   ├── candidates.jsonl          # generate checkpoint (append-only)
│   ├── validated.jsonl · judged.jsonl
│   ├── metadata.jsonl            # all candidates + checks + scores + decision

│   └── _manifest.json
└── cache/  llm/ · compile/ · http/

Configuration

Precedence: environment variable > .env > config/pipeline.yaml > code default. Values are checked at startup, so a bad config fails before any work starts.

.env (never committed)

OPENROUTER_API_KEYLLM access
LLM_BASE_URLOpenRouter by default; any OpenAI-compatible endpoint works
QUESTION_GEN_MODEL · ANSWER_GEN_MODELGeneration models
JUDGE_MODELMust be a different model family from the answer model
EMBEDDING_MODELIts max length limits the chunk token budget
GITHUB_TOKEN · GCS_BUCKETOptional

config/pipeline.yaml (committed)

sourcesRepo allowlist, Central orgs, sitemaps
crawlUser-agent, concurrency, delays
chunkmax_tokens, chunker version
generateTask quotas, top-k, requests per minute
judge.thresholdsfaithfulness ≥ 4, correctness ≥ 4, others ≥ 3
split.eval_fractionHeld-out documents, e.g. 0.05
validateBallerina version, pool size, timeout, heap

How to run

--limit N runs a small test, and --dry-run shows the plan without calling any model.

1

Set up once

python3.11 -m venv .venv && source .venv/bin/activate
pip install -e shared -r scraper/requirements.txt -e scraper \
  -r sft-dataset-generator/requirements.txt -e sft-dataset-generator
cp .env.example .env && bal version
2

Collect

python -m ballerinascraper.collect github
python -m ballerinascraper.collect central
(cd scraper/ballerinascraper && scrapy crawl web)
3

Process, generate and export (each stage can also run on its own)

sftgen all
# or: sftgen clean · extract · chunk · index · generate · validate · judge · export

Resuming after a failure

MechanismHow it works
Stage manifeststatus: running → completed | failed. Re-running a stage that didn't complete resumes the same run, if its input hashes haven't changed.
Item checkpointsgenerate, validate and judge append and flush one line per item. On resume, IDs already written are skipped.
Atomic outputsBatch stages write *.tmp and rename it when done. A half-written file is never read.
Deterministic IDs + upsertRe-runs never duplicate records or vectors.
CachesLLM responses and compile results are cached on disk, so repeated work costs nothing.
Item failuresRecorded in manifest.errors; the run continues. --retry-errors retries only those items.

Reliability, politeness and safety

ConcernApproach
ScrapingObeys robots.txt. One honest user-agent. AutoThrottle, ≤ 2 requests per domain, ETag. No proxies, no user-agent rotation.
HTTP retriesBackoff that honours Retry-After and GitHub's rate-limit reset.
LLM callsSDK retries with backoff; no retries on 400 or 401. Semaphore plus a requests-per-minute limit per model. JSON outputs checked against schemas.
Compiling generated codeCompile only, never run. Temp working folder, --offline, 60 s timeout, -Xmx1g, pool of 4.
LoggingJSON logs with run_id, stage and item ID. Funnel counts saved in manifests.
SecretsOnly in the environment. Redacted in logs and manifests.
License and contaminationSPDX license per record. Train/eval split per document. Retrieval limited to the seed's split. 13-gram overlap check.
